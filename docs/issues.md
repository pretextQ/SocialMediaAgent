## 1. 测试「定时炸弹」：硬编码日期锚点

**现象**：交接文档写着「全量 pytest **254 passed**」，但重跑时是 **247 passed / 7 failed**。

**影响**：项目自称「测试全绿」的说法**失效**；CI 一旦接入就会红。而且这类失败会随时间推移**持续恶化**，不是偶发。

**怎么发现的**：跑了一次全量测试。7 个失败集中在趋势相关用例，报错都是「期望 2 个话题，实际 0 个」。

**根因**：测试夹具把话题的 `last_seen` 写死成 `datetime(2026, 8, 24, 12, 0, tzinfo=utc)`，而被测代码 `get_trend_data` 用**真实墙钟**计算窗口 `since = now - period`。运行日期一旦超过「种子日期 + 周期」，种子数据就全部落在窗口之外被过滤掉。

**修复**：把夹具锚点改为相对当前时间（`datetime.now(timezone.utc)`），断言一行未改。

**额外收获**：顺手全量扫描同类问题，又发现 `test_memory.py` 的 TTL 用例把「有效条目」设为 `NOW + 30 天`，**将在 2026-09-23 之后开始失败**——同类缺陷要全量扫，而不是只修眼前红的 7 个。

**可迁移的教训**：

- 任何「与当前时间比较」的逻辑，测试都**不能**用硬编码时间锚点。
- 「测试全绿」是一个**有时效性的断言**；没有 CI 持续跑，它会悄悄变质。

## 2. 一个基于错误前提的「技术债」

**现象**：交接文档的待办清单写着：「`httpx2` 仅 `tests/unit/test_llm_gateway.py` 使用且未声明——替换为 `httpx.MockTransport` 或声明为 dev 依赖」。看起来是一项该清理的技术债。

**怎么发现的**：动手前先核实前提——读了 `openai` 包的元数据：

```
Requires-Dist: httpx2<3,>=2.7.0
```

**结论**：`httpx2` 是 `openai 3.x` 的**硬传递依赖**，只要装了 openai 就一定存在，**根本不是 CI 阻塞项**；而按原建议改成 `httpx.MockTransport` 反而可能因为 SDK 内部用的是 httpx2 而失效。

**修复**：**不改**，并在状态文档中纠正该条目的描述。

**可迁移的教训**：

- **别人写的待办也可能基于错误前提**——包括过去的自己。修之前先验证前提，成本远低于改错。
  - **复现（2026-09-12，死代码清理）**：待办把 `normalizers/ids.py::canonical_id` 与另三处并列在「死代码清理」下，
    但核实后它被 `normalizers/__init__.py` 公开导出、且 `test_normalizers.py` 正在断言它——问题是「**重复**」而非「**无引用**」。
    按清单直接删，删掉的是**被测的公开 API**。标签会骗人，引用关系不会。
- 「未在依赖清单里显式声明」和「不可靠」是两件事：要看它是不是上游的硬依赖。

## 3. 加抽象方法导致实现类无法实例化

**现象**：为支持 function calling，新增了 `ToolCallingProvider`（`LLMProvider` 的子类，含抽象方法），并让既有实现类 `OpenAICompatProvider` 继承它。

**怎么发现的**：先写测试、跑测试，RED 阶段直接报：

```
TypeError: Can't instantiate abstract class OpenAICompatProvider
           without an implementation for abstract method 'complete_with_tools'
```

而且它**中断了集成测试的收集阶段**（`ERROR collecting tests/integration/test_llm_injection.py`）。

**影响**：若直接提交，整个 API 模块在 import 时就会炸——启动即失败。

**修复**：为 `OpenAICompatProvider` 实现 `complete_with_tools`（请求携带 `tools`，解析 `tool_calls`）。

**可迁移的教训**：

- 给类新增抽象方法属于**破坏性变更**；用「新增子类」而不是「改基类」能隔离大部分风险，但一旦让既有实现继承新子类，就必须同时补齐实现。
- 这类错误在**收集/导入阶段**就会暴露，而不是运行到某条路径才炸——所以「先跑测试」能提前拦住它。

## 4. 写死的步数预算让功能「看似可用实则必然回退」

**现象**：评测中 llm 模式得分异常：

```
WARNING agentic gather 回退确定性路径: 达到最大步数（6）仍未结束
assert 0.0 == 1.0   # exact_match_rate
```

**根因**：`max_steps` 是 **LLM 往返轮次**上限。若模型**逐个**调用 6 个工具（6 轮）再给出最终回答（1 轮），就需要 7 轮，而默认值是 6——**永远走不完**。

**最危险的地方**：它**静默回退**到确定性路径。所以表面上「功能正常、有输出」，只有日志里一行 WARNING 能看出来。此前手工验证「成功」纯属侥幸：真实模型恰好把多个工具合并在几轮里返回。

**修复**：预算改为随工具数自适应 `len(tools) + 2`，并补一个聚焦测试：「6 个工具逐个调用 + 最终回答」必须在默认预算内跑完。

**可迁移的教训**：

- 写死的预算参数必须和**可用资源数量**挂钩（工具数、页数、重试对象数）。
- **静默回退是危险的**：回退必须可观测。因此已在 state 中记录 `gather_source`（`llm` / `rules`），让「这次到底是模型决策还是规则兜底」一眼可见。

## 5. 度量口径错误：被测对象被无关调用污染

**现象**：规则模式下实测到的工具集合，比预期多出一个 `save_operation_memory`。

**根因**：评测最初直接运行**整张 Agent 图**，而图里的 `persist` 节点会调用 `save_operation_memory`。但那是「**写记忆**」，不是「**选择取数工具**」——把它算进「工具选择质量」是**口径错误**。

**修复**：评测只测量 **gather 阶段**，不跑 analyze / persist / report。顺带也让评测更快、更便宜。

**可迁移的教训**：

- **先定义口径，再写度量**。「测什么」比「怎么测」更容易出错。
- 口径错了会得出**看起来正常但错误**的数字——后者比测不出来更危险。

## 6. Excel 默认 GBK 编码 + 部分写入脏数据

**背景**：为让「手工整理真实数据」这条路径可用，写了 CSV 导入命令。

**怎么发现的**：不是等用户报错，而是**推演真实操作路径**——使用者会在中文 Windows 上用 Excel「另存为 CSV」，而它**默认写 GBK**，命令只按 UTF-8 读就会抛 `UnicodeDecodeError`。同时发现另一个隐患：原实现**逐行写库**，第 20 行出错时前 19 行已经入库了。

**修复**：

- 依次尝试 `utf-8-sig / utf-8 / gb18030`，失败时提示「另存为 -> CSV UTF-8」。
- 改为**先整体校验、再写库**，任一行非法则整体失败，绝不留下半份数据。
- 增加 `--dry-run`，让使用者在落库前自检。

**可迁移的教训**：

- 要站在**真实使用路径**上推演（谁、在什么环境、用什么工具、会怎么操作），而不是只等测试或用户报错。
- 批量写入应当是**全有或全无**的，不能留下部分状态。

## 7. 工具输出不诚实：把「处理次数」当「库内数量」

**现象**：导入 50 行 CSV 后命令打印 `accounts=50`，但库里实际只有 **2** 个账号。

**根因**：计数器统计的是「处理了多少行（发生了多少次 upsert）」，而不是「库内去重后的数量」。50 行里有 2 个账号，幂等 upsert 把它们合并成 2 条——计数与事实不符。

**修复**：改为汇报**库内实际（去重后）数量**，并保留「处理行数」作为另一个字段。

**可迁移的教训**：

- **工具的输出也是接口**。误导性输出比没有输出更糟——使用者会基于它做出错误判断。
- 存在幂等/去重逻辑时，「输入条数」与「落库条数」必须分开表述。

## 8. 我自己的验证错误：默认 limit=100 静默截断

**现象**：我一度报告导入后「metrics = 100」，并据此怀疑数据有问题；实际库内有 **250** 条（50 内容 × 5 指标）。

**根因**：`BaseRepository.list()` 的签名是 `limit: int = 100`。我在核对数据时**没显式传 limit**，于是被静默截断到 100——**测量工具本身出了问题，我却差点把它当成被测对象的缺陷**。

**修复**：核对时显式传大 limit（`limit=10**9`）。

**顺带的真实发现（已修复）**：`api/routers/accounts.py` 调用 `AccountRepository.list(platform=...)` 同样没传 limit，意味着 **`GET /accounts` 会静默最多返回 100 条**。数据量小时看不出来，量上来就是隐性 bug。

> **修复（后续补）**：该端点原先**根本不接受 `limit` 参数**（FastAPI 静默忽略未知查询参数），所以上限既隐性又无法调高。现显式暴露
> `limit`（默认 100 / 最大 500，与 `/contents`、`/metrics` 对齐），MCP 的 `list_accounts` 同步支持；回归测试为
> 「120 个账号 → 默认返回 100，传 `limit=500` 取回 120」。
> 注意：这只修了「**无法调高上限**」，不是「取消上限」——无界查询同样不可接受。

**可迁移的教训**：

- 默认参数会**静默截断**；读到「整数」时要问一句「这个数字是不是被谁设了上限」。
- **核对数字时也要怀疑测量方式**：把工具的问题误判成系统的问题，会导出错误结论。

## 9. 文档跑在实现前面

**现象**：架构文档的 P2 DoD 明确写着「**P3 起由 LLM 决策工具调用**」，但直到 P5.5（又过了三个版本）代码里仍是**正则路由 + 固定调用**，这个承诺从未兑现。

**影响**：下一个接手的人（包括几个月后的自己）会**基于文档做出错误判断**，以为系统已经具备该能力。

**修复**：把「承诺」与「现状」拆成两份文档——架构文档只描述**现状**，进度与未完成项集中到状态文档。

**可迁移的教训**：

- 文档里的**承诺要能被验证**；不能验证的承诺会变成误导。
- 「已完成」这类状态信息应当**只有一个来源**，多处记录必然不一致。

> **后续（2026-09-12）**：那条「P3 起由 LLM 决策工具调用」的承诺现已兑现——`account_strategy.gather`（M2）与
> 最小图的指令路由（B1，`agents/router.py`）都支持 LLM 决策，且默认关闭、失败回退。此处保留原文，
> 因为它记录的「承诺跑在实现前面」这个更普遍的问题，并不因某一处补上而消失。

## 10. 授权「编造数据」时的边界处理

**背景**：为了让评测有数据可用，需求方明确授权「可以编造数据来验证」。

**处理方式**：把「能不能做」和「该怎么做」分开——可以造数据用于**验证链路**，但不能让造的数据**冒充真实数据**（那会让评测结论彻底失效）。具体做法：

- 新增 `MetricSource.SYNTHETIC` 枚举值，让「假的」在**数据本身**里可被识别，而不是靠记忆；
- 导入独立 demo 库，不混入真实数据库；
- 生成器随代码提交，数据文件不入库（可复现、不会与生成器脱节）；
- 在文档中写明：合成数据**仅用于链路验证与演示，绝不可作为评测依据**；评测的 ground truth 只能来自真实数据。

**可迁移的教训**：

- **授权不等于放弃判断**。拿到「你可以这么做」时，仍要问「怎么做才不破坏结论的可信度」。
- 对「数据来源」这类信息，**标记在数据里**（而不是写在注释或记忆里）才靠谱。

## 11. 组合出的能力重复取数：评测指标把 bug 当成了「基线」

**现象**：工具选择评测里，确定性（rules）路径每例发生 **9 次**工具调用、去重后只有 **6 个**工具——
`get_account_profile` / `get_recent_contents` / `get_trend_data` 各被调了两次，每例重复 3 次。

**怎么发现的**：不是读代码推出来的，是**度量出来的**。M3 做工具选择评测时，用 `RecordingRegistry`
包住真实 `ToolRegistry`，记录**实际**调用序列（而不是引用手写常量），第一次跑就打印出
9 次调用 / 6 个工具。若只靠读代码或假设，这个重复很可能一直留着。

**根因**：`account_strategy.gather()` 直接调用了 `topic_recommendation.gather()` 来拿选题候选。
后者是一个**完整能力**，会重建自己的上下文（profile / recent / trends），于是同一批数据被请求两遍。
即：**「能力组合」被实现成了「重新执行整个子能力」**，而不是「复用子能力的取数结果」。

**修复**：抽出 `gather_context()`（profile / recent / trends 只取一次），
`topic_recommendation.gather()` 与 `account_strategy.gather()` 复用它；
account_strategy 只额外取 performance / history / knowledge。
策略侧原本只看 5 条近期内容，共享上下文按 20 条取数后**切片到 5 条**——
**去重不应顺带改变注入 LLM 的 facts 形状**。

**验证（可复核）**：`evaluation` CLI，同一批 2 个用例、`--runs 3`：

| 模式 | before 重复调用 | after 重复调用 |
| --- | --- | --- |
| rules | 3.00 ± 0.00 | **0.00 ± 0.00** |
| llm | 0.33 ± 0.24 | 0.17 ± 0.24（LLM 随机性，与本次改动无关） |

**附带发现（同一轮暴露的方法论问题）**：最初只跑**一轮**，LLM 路径的重复调用正好是 0、
完全匹配率 100%，看起来「LLM 比规则干净得多」；改成多轮取均值 + 方差后，LLM 的完全匹配率
其实是 **83% ± 24%**（有的轮次漏调 `search_operation_knowledge`、有的轮次重复调 `get_trend_data`）。
**单次运行会给出看似精确的错误结论**——温度 > 0 的模型评测必须报告方差，这就是 `--runs` 默认 3 的原因。

**可迁移的教训**：

- **组合能力要复用的是「数据」，不是「子能力」。** 直接调用另一个能力的入口函数，
  等于把它的 I/O 也一并复制；层与层之间应传递已取到的事实。
- **度量要记录「实际动作」，不要记录「你以为的动作」。** 真实调用序列会说话，手写常量一定
  会和实现悄悄脱节（本文件 #5 已经栽过一次口径的坑）。
- **指标出现「稳定的大数」时，要问一句它是不是 bug。** 修复前那条
  `assert rules.total_duplicate_calls > 0` 已经把缺陷写成了「规则基线的特征」——
  **测试固化了错误行为**。改测试预期是必要的，但必须说清这是「需求变更」而非「为了变绿」。

## 12. 接 Alembic 时踩的三个坑

**背景**：给项目补版本化迁移（此前用 `Base.metadata.create_all`，表结构一变只能重建库）。

**坑 1：ini 被系统 locale（GBK）读，写中文直接炸。**

- 现象：`alembic revision` 报 `UnicodeDecodeError: 'gbk' codec can't decode byte 0xb1`。
- 根因：Alembic 用 `encoding="locale"` 读 `alembic.ini`，中文 Windows 上是 GBK；而我往 ini 里加了中文注释。
- 修复：`alembic.ini` **保持纯 ASCII**，说明挪到 `migrations/README`。

**坑 2：autogenerate 漏掉自定义类型的 import。**

- 现象：迁移能生成、**不能跑**——`NameError: name 'socialmedia_agent' is not defined`
  （渲染出 `socialmedia_agent.database.base.UTCDateTime()` 却没有对应的 import）。
- 修复：在 `script.py.mako` 里固定加 `import socialmedia_agent.database.base`，以后每份迁移都自带。

**坑 3（最危险）：收养既有库时 `stamp head` 会把未执行的迁移标记成已完成。**

- 现象：`test_drops_legacy_comments_table` 红——既有库升级后 `comments` 表**还在**。
- 根因：既有库没有 `alembic_version`，直接 `upgrade` 会因「表已存在」失败，所以我先 `stamp head`。
  但此时 `head` 已经是**新的「删表」迁移**，stamp 等于宣布它已执行 → 它永远不会跑。
- 修复：收养时 stamp **基线版本**（`ScriptDirectory.get_base()`），再 `upgrade head`。

**可迁移的教训**：

- **「让状态位指向最新」是危险的默认直觉**：stamp 的语义是「**已经执行到哪**」，不是「想升到哪」。
  二者混用会**静默吞掉迁移**——不报错，但该做的事没做。
- 这个坑不是靠读文档发现的，是**测试先红**发现的；而那条测试测的正是「既有库升级后旧表应该消失」。
  **能观察到副作用的测试**（表在不在）比「调用没报错」强得多。
- 跨平台项目里，**配置文件也有编码**；往 ini 写非 ASCII 之前，先确认读它的程序用什么编码。

## 13. 装了两份 vite：同名类型不兼容

**现象**：新增前端后 `npm run build`（`tsc --noEmit && vite build`）失败，报错指向 `vite.config.ts`：

```
Type Plugin (from node_modules/vite/dist/node/index) is not assignable to
type Plugin (from node_modules/vitest/node_modules/vite/dist/node/index)
```

**怎么发现的**：不是靠猜，是 `tsc` 直接给出的完整类型链。
关键线索是路径里出现了**两处 vite**：`node_modules/vite` 与 `node_modules/vitest/node_modules/vite`。

**根因**：`vitest@2` 的 peer 依赖是 `vite ^5`，而项目装的是 `vite ^6`。npm 无法 dedupe，
于是**在 vitest 下嵌套安装了第二份 vite 5**。`vitest/config` 的 `defineConfig` 用的是嵌套那份的插件类型，
而 `@vitejs/plugin-react` 用的是顶层 vite 6 的类型——两套 `Plugin` 类型名义相同、结构不兼容。

**修复**：把 `vitest` 升到 **v3**（peer 支持 `vite ^5 || ^6`），npm 随即复用顶层 vite，嵌套目录消失，类型冲突一并消失：

```
node_modules/vitest/node_modules/vite   -> 不存在
vite 6.4.3 / vitest 3.2.7
```

**可迁移的教训**：

- **「同名类型不兼容」几乎总是「装了两份」**。看错误信息里的完整路径，比读类型定义快得多。
- 引入新依赖时要看它的 **peer 依赖范围**是否与项目现有版本重叠；不重叠就会嵌套安装。
- 这类问题不是代码 bug，是**依赖图问题**；用 `as any` 去压制只会把它藏起来。

## 14. 配置项只被「读侧」使用：写读不同源

**现象**：为前端新增 `GET /reports` 后，周报页能列出文件，但**永远读不到调度器写出的周报**。

**怎么发现的**：核对交付时逐条追「这个配置项被谁用了」。结果 `SMA_REPORT_DIR` 只有
`reports.py` 与 `system_status.py` 两个**读侧**在用；而**写侧** `generate_all_weekly_reports(...)` 与
`create_weekly_report_scheduler(...)` 仍要求调用方显式传 `report_dir`——两者**没有任何绑定关系**。

**根因**：新增端点时只实现了「读」，把「写」的目录来源留在调用方，于是存在两条各自独立、
默认值可能不同的路径。这不是崩溃型 bug，而是**接线缺失**：单次演示中功能看起来完全正常。

**修复**：两个函数的 `report_dir` 改为 `str | None = None`，为 `None` 时回落 `Settings.report_dir`；
调用方行为不变（向后兼容），并补两条测试钉住默认行为。

**可迁移的教训**：

- **新增「读取某目录」的能力时，必须问：谁在写这个目录？两边是同一个值吗？**
  只写读侧会得到一个「不报错但永远为空」的功能——这类缺陷最容易被漏掉。
- 配置项的**每个使用点都要能被数出来**。只有一个使用点的配置项，通常意味着漏了另一半。

## 15. 文档再次跑在实现前面（README 三处过时 + status.md 自相矛盾）

**现象**：通读 `docs/` 时发现状态描述与代码不符：

| 文档声称 | 实际 |
| --- | --- |
| README「**无数据库迁移**，未接 Alembic」 | 早已接入（迁移 + 既有库自动收养 + 漂移守护测试） |
| README「P6 评估套件**其余 4 项尚未开发**」 | 5/5 全部实现 |
| README「**前端未实施**」 | 已实施 |
| status.md「P6 — 已实现 **1 项**；其余 4 项未开始」 | **同一份文档**第 7 节 E 组写着「5 项评估全部实现」 |
| status.md「测试 317 passed」 | 实测 **412 passed** |

**怎么发现的**：不是靠某一条报错，而是**交叉阅读**——把 `docs/` 与代码/实测逐条对照，
并且**同一份文档内部对读**（status.md 第 5 节与第 7 节互相矛盾）。

**根因**：这正是本文件 **#9 记录过的同一个问题**——进度型信息被写在多个地方。
#9 的修复是把「承诺」与「现状」拆开，但没有阻止「同一事实在不同文档各写一遍」；
README 的「已知限制」与 status.md 的「阶段对照」就是两个副本。

**修复**：本次一并更正 README 三处、status.md 两处，并把「前端已实施」同步到
`architecture.md`（分层图 / 目录 / 模块职责）、`api.md`（新端点与 `source` 语义）、
`plan-frontend.md`（第八节实施结果）、`adr/0005-frontend.md`（决策留痕）、`eval/README.md`（新证据）。

**可迁移的教训**：

- **「文档对不对」不能靠读一份判断，要靠对读**：文档 ↔ 代码、文档 ↔ 实测、文档 ↔ 文档。
- 「已完成 / 未完成」这类状态**必须只有一个物理位置**；只要允许副本存在，副本一定会腐烂。
- 这条与 #9 是**同一条教训的第二次复发**——说明「加一条规则」不够，
  要能**机械化检查**（例如让测试断言文档中引用的测试数与实际一致）才可能真正防住。

## 16. 收养既有库时，新增表的迁移撞上「已是最新 schema」的库

**现象**：为时间序列新增两张观测表并生成 Alembic 迁移后，**45 个测试同时变红**，
报错清一色是：

```
sqlite3.OperationalError: table topic_observations already exists
```

**怎么发现的**：跑了一次全量测试。45 个失败里既有单元也有集成，
但错误信息指向**同一张表**——这说明不是 45 个独立 bug，而是**一条公共路径**出了问题。

**根因**：`upgrade_to_head` 的**收养逻辑**（正是本文件 #12 的产物）对
「由 `create_all` 建、没有 `alembic_version` 的库」的策略是
**stamp 基线 + 重跑全部增量迁移**。

问题在于：`create_all` 用的是**当前的**模型定义，所以它建出来的库**已经是最新 schema**。
于是任何「**新增表**」的迁移，都会在收养路径上与已存在的表冲突。
`drop comments` 那条迁移之所以没出事，是因为它写成了**存在性守卫**（存在才删）；
当时加守卫的理由是「全新库上应为空操作」，恰好也躲开了这个坑。

**为什么 45 个测试都中招**：几乎所有集成测试都用 `with TestClient(app)`，
而应用 lifespan 会调用 `upgrade_to_head`；测试库又是先 `create_all` 建的——
于是**每个**集成测试都走了一次收养路径。

**修复**：新迁移的 `create_table` 加存在性守卫（与 `drop comments` 同一条约定），
并在迁移文件里写明原因；`downgrade` 同步加守卫保证可重复执行。

**可迁移的教训**：

- **「收养既有库」等价于「在未知版本的 schema 上重跑全部增量迁移」**。
  因此每条迁移都必须**幂等**，不能假设目标对象一定不存在。
  自动生成的迁移**天然不幂等**：autogenerate 只知道「目标 schema 该长什么样」，
  不知道「当前库可能已经长这样」。README 里那句「务必人工审阅生成的文件」是有牙齿的。
- **一次改动让几十个测试同时变红时，先找公共路径，别逐个看**。
  45 个失败里没有一个是独立 bug；**错误的同质性**才是根因唯一的信号。
- 这条与 #12 是**同一处代码的第二次咬人**：#12 修的是「stamp head 会吞掉迁移」，
  修完得到「stamp 基线 + 重跑」；但那个补救方案**给每条迁移加了一条隐含契约（必须幂等）**，
  当时没有写下来。**修一个坑时，要把补救方案引入的新契约一并写清楚**，
  否则下一次改动会从另一个方向撞上它。
